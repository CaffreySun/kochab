# 0012 跨窗口共享的录屏状态

- 状态：已采纳
- 日期：2026-10-17

## 背景

录屏最初只有设备菜单里的一个弹窗：弹窗自己记时间、自己开始/停止。设备页与投屏窗口
是独立 webview，这带来三个问题：

1. 在投屏窗口看不到设备页是否已经在录屏，点第二次只会得到 `already_recording`；
2. 弹窗卸载（切面板、关窗口）会顺带停止录制，而投屏中断不应该打断录屏；
3. 180 秒时限、设备断开、重复停止等边界没有统一处理。

## 决策

### 1. 真值放在 Rust

`AppState.recordings: Map<serial, Recording>` 是唯一状态。新增：

- `device_record_status`：只读内存，返回 `{ active, startedAt, maxSeconds }`；
- `device_record_cancel`：放弃状态并尽力删除设备端临时文件；
- `device_record_stop` 改为幂等：没有进行中的录制时返回 `null`，不报错；
- 开始/停止/放弃都广播 `recording://changed`。

`Recording` 增加 `started_at`（Unix 毫秒），前端读秒以它为准，而不是组件挂载时间。

### 2. 前端 `useRecording(serial)`

设备页卡片、设备「更多」菜单、投屏窗口各自挂一个实例：

- 挂载时查询状态，并订阅 `recording://changed`；
- 任一路由开始/停止，其它窗口立即同步；
- 卸载时**不停止**录制；
- 到达 `maxSeconds` 自动调用 stop（幂等），第一个真正拉到文件的实例提示保存路径；
- 组件只负责提示错误，不维护第二份状态。

### 3. 入口

- 设备卡片右侧竖排栏新增录屏按钮；录制中显示红色读秒徽标；
- 投屏右侧竖排栏新增录屏按钮；画布右上角显示「录制中 mm:ss」胶囊；
- 设备「更多」菜单的「开始/停止录屏」与「放弃录屏（不保存）」。

## 边界处理

| 场景 | 行为 |
| --- | --- |
| 投屏中断/停止/重连 | 录屏与 scrcpy 会话完全解耦，继续录制；徽标仍在 |
| 横竖屏切换 | 录制不重启；screenrecord 输出尺寸保持开始时的方向，文件仍可播放（真机验证） |
| 切换面板 / 关闭设备窗口 | `useRecording` 卸载不停止；录制继续，卡片/其它窗口仍显示状态 |
| 180 秒时限 | 任一挂载实例自动 stop 并拉取；重复 stop 幂等，只有一次保存 |
| 同一设备重复开始 | 后端返回 `already_recording`，UI 只提示，不产生第二条记录 |
| 设备断开 | 状态仍可查询；停止会报错并保留句柄，设备恢复后可重试；也可「放弃录屏」 |
| 应用崩溃/强退 | 设备端进程最多跑到 180 秒；下次启动清理 10 分钟前的 `ac-rec-*` 临时文件 |
| 多窗口同时操作 | 事件广播 + 幂等 stop，最多保存一份文件 |

## 已知限制

- 应用退出时无法拉取正在录制的文件；只能依赖设备端时限与下次启动清理。
- 旋转后 MP4 保持开始时的分辨率（例如 1080×2160），不会切成两段。
- 录屏与投屏画质参数无关，使用设备端 `screenrecord` 的 8 Mbps / 180 秒上限。

## 验证

- 真机横竖屏：录制中 `user_rotation 1 → 0`，停止后 MP4 `duration=7.2s`、H.264、1080×2160，可正常解析。
- 前端：卡片开始/停止并显示读秒、投屏栏开始/停止并显示录制徽标、菜单开始/停止并提示保存路径；Vitest 全部通过。
- Rust：命令契约双向一致；`screenrecord` 启动/停止链路复用 0010 的真机验证。
