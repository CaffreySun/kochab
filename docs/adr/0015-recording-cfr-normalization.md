# 0015 录屏保存后补帧为 CFR

- 状态：已采纳
- 日期：2026-10-19

## 背景

真机反馈：录屏开头有一段无法播放，长度取决于开始录屏后画面静止了多久；
画面第一次变化后恢复正常。例如静止 3 秒，前 3 秒不能播；静止 7 秒，前 7 秒不能播。

用 `ffprobe` 检查设备产物：

```text
packet pts=0.000  duration=1.170  flags=K
packet pts=1.170  duration=0.018
packet pts=1.188  duration=1.200
packet pts=2.388  duration=4.475
packet pts=6.863  duration=0.028
...
```

`screenrecord` 使用 Surface 输入，画面不变时编码器不出帧，MP4 因此是
可变帧率（VFR），静止段会出现 1~7 秒的单帧时长。Windows「媒体播放器」
会在这类文件的开头一直黑屏，直到遇到下一段密集帧；Chrome / ffmpeg
能解码，但这不是可接受的跨播放器行为。

另有一个更极端的边界：完全静止的短录屏可能只写出 **1 帧**，且该帧
`duration=0`；直接读取时会被压成微秒级。

## 决策

录屏拉到本机后、返回保存路径前，做一次**不重新编码**的 MP4 重封装：

- 读取原视频轨的样本（已经是长度前缀的 AVCC 数据），按原始 PTS 计算每帧应占的时长；
- 相邻帧间隔超过 100ms 时，重复上一帧的编码数据，直到填满该间隔；
- 单帧 / 末帧 `duration=0` 时，用 `stop_recording` 入口处记录的
  「`now - started_at`」实际录制时长兜底；
- 输出时间基固定为微秒，样本顺序与内容不变；
- 先写临时文件，成功后再覆盖原文件；任何一步失败都保留原始文件，
  只记录 warning，不让用户丢失录屏。

重复帧共享原始 H.264 的 `frame_num`，主流解码器会复用参考帧；静止画面
重复同一帧不会产生可见画质损失。100ms 是折中：既让播放器有足够密集的
样本，也不会把 180 秒静止录屏的体积放大太多。

## 备选方案

| 方案 | 放弃原因 |
| --- | --- |
| 改用 scrcpy 编码器 | scrcpy server 设置 `KEY_REPEAT_PREVIOUS_FRAME_AFTER=100ms`，能直接产出密集帧；但要把 H.264 流在桌面端重新封装，且录屏会依赖投屏会话，设备断开/窗口关闭即中断，不如设备端 `screenrecord` 稳 |
| 内置 ffmpeg 转码 | 体积大、跨平台分发复杂；用户明确不希望捆绑 ffmpeg |
| 只把长帧时长截短 | 时间轴被压缩，录屏时长和音画同步都会错 |
| 只修第一段 | 后续静止段仍可能黑屏；补帧应覆盖全部大间隔 |

## 后果

- 静止画面按 10fps 保存，画面变化时保留原始帧率；最大帧间隔 100ms。
- 文件体积增加取决于静止时长和关键帧大小；静止时重复的是最后一帧，
  测试样本增加约 4%。
- 带音轨或非 H.264 的输入直接跳过补帧，保留原文件。
- 旧录屏不会自动修复；只影响此后保存的文件。

## 验证

- 单元测试：3 秒稀疏 VFR → 最大帧间隔 ≤100ms、总时长不变；
  单帧 `duration=0` + 2 秒实际时长 → 补出 ≥20 帧、时长 2 秒。
- 真机集成测试：录制 1.2 秒后停止，读回 MP4 断言存在视频轨、
  样本数 >1、最大帧间隔 ≤100ms。
- 真机 4 秒静止录屏：保存后 `ffprobe` 为 41 帧 / 4.014 秒 / 最大间隔
  100ms，Windows 媒体播放器从第 1 秒即可正常显示，画面变化后内容正常。
