# ADR-0008：控制消息在 Rust 侧编码

- 状态：已采纳
- 日期：2026-10-15

## 背景

投屏要能交互，就得把「用户操作」变成 scrcpy 的控制消息字节写到控制 socket。
这些字节的布局只有一处权威实现：`crates/scrcpy-protocol`（附单测）。

前端要发的是**语义事件**：这里点了一下、按了返回键、滚了 3 格。
问题是这层语义在哪里变成字节。

## 决策

渲染进程只把**语义事件 + 设备像素坐标**发到 Rust：

| 命令 | 参数 |
| --- | --- |
| `session_touch` | `action`（down/move/up）、`x`、`y` |
| `session_key` | `keycode`、`pressed` |
| `session_text` | `text` |
| `session_scroll` | `x`、`y`、`hScroll`、`vScroll` |

Rust 用 `scrcpy-protocol` 编码后写入控制 socket。

坐标换算留在渲染进程（`@ac/scrcpy-web` 的 `clientPointToDevice`），
因为只有它知道画布的实际显示尺寸。

## 理由

1. **字节布局只有一处实现**。若让前端编码，`scrcpy-protocol` 与 TS 就会各有一份，
   而两者只能靠人肉保持同步——协议一改就是难查的错位 bug。
2. **可测性**。Rust 侧的编码有精确到字节的单测；前端只需要测「点击是否映射到
   正确的设备坐标」。
3. **控制通道的并发与生命周期在 Rust**。会话对象、socket、停止信号都在那边，
   前端多持有一份编码逻辑只会让边界更模糊。

## 代价

- 每个交互过一次 IPC。实测这层是进程内调用，开销远小于一次触摸往返。
- 前端失去了「构造任意控制消息」的能力。当前不需要；真需要时再加一个
  显式的原始字节命令，而不是把编码逻辑搬过去。

## 与既有文档的出入

`docs/ARCHITECTURE.md` 早期版本写的是「渲染进程编码字节 → `session_send_control`」，
并同时声称「字节布局的唯一实现只有一处」——这两句本身是矛盾的。
本 ADR 取后者，前者作废。
